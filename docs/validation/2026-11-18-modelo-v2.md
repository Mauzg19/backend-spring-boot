# Integración del modelo de demanda v2

Actualización del 18/11/2026. Modelo `demanda-mlp-v2-seed42`, arquitectura 13 → 32 → 16 → 1, 993 parámetros. MAE 3,0504 y ejemplo Hamburguesa 01/09/2026 con historia 38/40/65,71428571428571 → 49,577291514433696. Evaluación retrospectiva sobre los mismos datos sintéticos que v1. Comparación descriptiva, reducción del MAE del 3,82%.

## Contrato y cambios

Se conservan GET `/api/admin/demand/report` y POST `/api/admin/demand/predict`. El cuerpo sigue siendo `product`, `date`, `lag1`, `lag7`, `mean7`. Los pesos y el informe se publican juntos con la misma identidad. El backend rechaza pesos e informe de versiones distintas. El entrenamiento y Keras están en el backend, `mineria/README.md`.

La web obtiene del informe el identificador, arquitectura, entrenamiento y unidades de la curva (`historyMetric`). Flutter muestra el identificador y el MAE recibidos y conserva la inferencia en Spring. Los reportes v1 continúan siendo legibles por ambos clientes. Los ejemplos se cargan del servidor.

## Evidencia local

Se cotejaron 300 respuestas HTTP de cinco productos y todos los días de semana con la referencia Keras congelada. Diferencia máxima 0,00000962 unidades. Web verificada tres veces, cinco escenarios, roles propietario/admin 200 y cliente/gerente 403, tres anchos, rechazo de historia negativa y recuperación tras 503. Un mutante de +10 unidades falló exactamente por discrepancia numérica. Resultado portable en `integracion-modelo-v2.json`.

Comandos ejecutados desde cada proyecto, capturados con codex-check.py y salidas nativas. Backend `mvn -q package` y `python -m unittest discover -s mineria -p test_pipeline.py -v`. Web `npm run build` y `react-scripts test --watchAll=false --runInBand`. Flutter `flutter test --no-pub` y `flutter analyze --no-pub`.

El build web estándar completa con advertencias heredadas de imports y dependencias de hooks en componentes externos al módulo. El modo CI estricto conserva un resultado fallido por esas advertencias. No se modificaron los niveles de ESLint.

## Prueba nativa reproducible

Flutter incluye `integration_test/demand_v2_test.dart`. Requiere un backend de QA aislado con los usuarios ficticios `cocina-aula@example.test`, `admin-aula@example.test`, `cliente-aula@example.test`, `gerente-aula@example.test`, contraseña `AulaDemo2026`. Esta fixture usa los roles del proyecto y una base sintética nueva. No usar cuentas operativas. Publicar la API local en 15454 y ejecutar `adb -s emulator-5570 reverse tcp:15454 tcp:15454`.

Desde `restaurantapp`, ejecutar `flutter test integration_test/demand_v2_test.dart -d emulator-5570 --dart-define=BACKEND_BASE_URL=http://127.0.0.1:15454 --no-pub`. Abre la pantalla nativa real, usa sesión JWT real, verifica cinco predicciones contra Keras, permisos y pérdida/recuperación de conexión. El control negativo se activa con `--dart-define=DEMAND_MUTANT=true` y debe fallar por comparación de la cifra mostrada.

Resultados actuales: 30 pruebas Java, 2 Python, 6 React y 63 Flutter aprobadas, análisis Flutter sin incidencias. Tres recorridos web y tres nativos Android aprobados, más una repetición nativa final con el control negativo restringido al endpoint de predicción. El mutante Android +10 falló por la cifra mostrada, con el mensaje `V2 prediction must match frozen Keras result`. El intento negativo anterior que alteraba también el login falló por preparación y se conserva como inconcluso. El APK normal de QA se compiló desde lib/main.dart y su hash está en el JSON de integración.

La evidencia completa local reside en `qa-modelo-v2-20261118/evidence` junto a los repositorios. Este cambio actualiza ramas de PR para revisión. Los videos y el informe entregado previamente conservan sus resultados históricos de v1. Teléfono físico y Stripe Test Mode continúan aplazados por decisión del usuario.
